# Обоснование выбора событийного подхода

---

## 1. Проблемы текущей архитектуры (Camel + DWH)

### 1.1 Монолитная бизнес-логика в DWH

Более 60% бизнес-логики компании «Будущее 2.0» реализовано в виде хранимых процедур, триггеров и ETL-процессов внутри DWH на SQL Server 2008. Это приводит к:

- **Высокой связанности** — изменение логики одного домена требует изменений в общей схеме DWH, затрагивая все connected-системы
- **Низкой тестируемости** — бизнес-правила, погребённые в SQL-коде, невозможно изолированно тестировать без полной копии DWH
- **Замедлению time-to-market** — каждое изменение требует ETL-разработки, тестирования на полном объёме данных и длительного развёртывания

### 1.2 ESB как точка отказа и узкое место

Apache Camel используется как центральная шина для всех интеграций. Это создаёт:

- **Транзакционную связность** — ошибка в одном потоке данных может заблокировать очередь и остановить интеграцию смежных систем
- **Отсутствие гарантий доставки** — при перегрузке или перезапуске ESB сообщения теряются
- **Сложность масштабирования** — Camel — единый процесс, горизонтальное масштабирование требует дополнительного слоя балансировки и ручного управления партициями
- **Синхронные паттерны** — часть интеграций построена на request/response, что создаёт блокировки между сервисами

### 1.3 Batch-ориентированная аналитика

Формирование отчётов в Power BI поверх DWH работает по расписанию (batch). Результат:

- Задержка данных от нескольких часов до суток
- Невозможность строить near-real-time дашборды для клиник и финансовых операций
- Конфликты ресурсов при одновременной загрузке нескольких ETL-процессов

## 2. Преимущества событийного подхода (Kafka + доменные события)

### 2.1 Слабая связанность (Loosе Coupling)

Каждый домен публикует события, ничего не зная о подписчиках. Подписчики сами выбирают, на какие события подписаться. Это позволяет:

- Разрабатывать, тестировать и деплоить домены независимо — команда Medical может менять свою логику, не спрашивая Fintech
- Добавлять новые домены без изменения существующей интеграции — достаточно начать подписываться на события
- Заменять легаси-системы поэтапно, не ломая общую картину

### 2.2 Гарантированная доставка и durability

Apache Kafka хранит события на диске с настраиваемым retention (от дней до месяцев). Даже если подписчик временно недоступен:

- События не теряются — при восстановлении подписчик прочитает все пропущенные сообщения
- Возможен replay — повторная обработка истории для починки данных или обучения ML-моделей
- Поддержка exactly-once семантики (через Kafka Streams / Flink)

### 2.3 Нативная масштабируемость

- Kafka горизонтально масштабируется добавлением брокеров и партиций
- Каждый подписчик обрабатывает события в своём темпе — медленный consumer не замедляет producers
- Пропускная способность измеряется миллионами событий в секунду (против тысяч у монолитного ESB)

### 2.4 Near-real-time аналитика

События могут одновременно:
- Обновлять операционные данные в домене-получателе
- Попадать в Data Lake (через Kafka S3 Sink) для долгосрочного хранения
- Обрабатываться в Stream Processor (Flink) для построения витрин в ClickHouse

Время от события до отображения в дашборде сокращается с часов до секунд.

### 2.5 Аудит и traceability

Каждое доменное событие — неизменяемый факт с timestamp и eventId. Это даёт:

- Полную историю изменений по каждой сущности (Event Sourcing-ready)
- Аудиторский след для соответствия требованиям регуляторов (ЦБ РФ, Минздрав)
- Debugging — можно воспроизвести цепочку событий, приведшую к конкретному состоянию

### 2.6 Data Mesh-ready

Событийная архитектура органично ложится на Data Mesh:
- Каждый домен публикует Data Product как поток событий
- Data Catalog (OpenMetadata) регистрирует схемы и контракты
- Data Marketplace предоставляет самообслуживание для аналитиков без нарушения границ доменов

## 3. Сравнительная таблица

| Критерий | Camel + DWH (текущее) | Kafka + Domain Events (целевое) |
|---|---|---|
| Связанность | Высокая (общая схема, хранимые процедуры) | Низкая (доменные события, неизвестность подписчиков) |
| Time-to-market | Недели (ETL + тестирование на полном DWH) | Дни (изменение в одном домене, независимый деплой) |
| Надёжность доставки | At-most-once (потеря при падении Camel) | At-least-once / exactly-once (Kafka persistence + offset commit) |
| Масштабирование | Вертикальное (один процесс Camel) | Горизонтальное (партиции брокера + параллельные consumer group) |
| Задержка аналитики | Часы (batch ETL) | Секунды–минуты (stream processing) |
| Аудит | Ограниченный (логи ETL, неструктурированные) | Полный (все события в топиках с retention) |
| Стоимость изменений | Высокая (каждое изменение затрагивает монолит) | Низкая (изоляция по bounded context) |
| Присоединение нового домена | Месяцы (согласование схемы DWH, ETL-разработка) | Дни (настройка своего брокера, публикация событий) |

## 4. Риски и митигация

| Риск | Митигация |
|---|---|
| Сложность отладки асинхронных потоков | Внедрение Distributed Tracing (Jaeger), Event Log Viewer, тестовых consumer'ов |
| Необходимость управления схемами | Schema Registry (Avro / Protobuf) с обязательным backwards-compatibility-check |
| ​Первичная миграция легаси | Anti-Corruption Layer (Debezium для CDC из SQL Server, Camel → Kafka адаптер) |
| Увеличение операционной сложности | Платформенная команда (Data Platform), IaC для Kafka на базе Terraform |
| Eventual consistency | Санация через компенсирующие события (Saga pattern) для критичных бизнес-процессов |

## 5. Вывод

Переход от монолитного DWH с ESB на событийную архитектуру на базе Kafka даёт компании «Будущее 2.0»:

1. **Независимость доменов** — каждая бизнес-единица (клиники, банк, ИИ-сервис, фарма, электроника) развивается в своём темпе
2. **Масштабирование** — инфраструктура растёт горизонтально вместе с количеством пациентов, транзакций и событий
3. **Скорость** — time-to-market сокращается с недель до дней, аналитика переходит из batch в near-real-time
4. **Готовность к Data Mesh** — событийная платформа является фундаментом для Data Products, Data Catalog и Marketplace

Событийная архитектура — не просто технологическое обновление, а стратегический фундамент для трёхлетней трансформации, заявленной в целевой архитектуре компании.
