# План управления рисками

## Риски с приоритетом «Высокий» (Влияние × Вероятность)

### R11 — Потеря бизнес-логики из Legacy DWH

- **Тип меры**: Технический + Организационный
- **Технические меры**:
  - Провести полный аудит хранимых процедур, триггеров и вьюх в SQL Server
  - Создать карту бизнес-логики с привязкой к доменам
  - Реализовать каждую бизнес-функцию как отдельный микросервис с тестами
  - Использовать Approval Tests для сравнения результатов старой и новой логики
- **Организационные меры**:
  - Привлечь бизнес-аналитика, знающего легаси-систему, на полный день
  - Провести сессии документирования бизнес-правил с представителями подразделений
- **Метрика**: 100% хранимых процедур задокументировано и покрыто тестами до отключения DWH

### R8 — Нехватка компетенций по Kafka, Flink, Data Mesh

- **Тип меры**: Организационный
- **Меры**:
  - Нанять 2–3 senior-инженеров с опытом event-driven архитектуры (Tech Lead + Platform Engineer)
  - Организовать внутреннюю программу обучения (Kafka Fundamentals, Flink, Data Mesh)
  - Внедрить практику pair programming на критических модулях
  - Заказать внешний аудит архитектуры раз в квартал
- **Метрика**: 80% команды прошло сертификацию Kafka/Data Mesh к концу 1 этапа

### R1 — Потеря данных при миграции из Legacy DWH

- **Тип меры**: Технический
- **Меры**:
  - Использовать Debezium с проверкой целостности (checksum) на каждом batch
  - Настроить Dead Letter Queue (DLQ) для всех ошибочных записей
  - Реализовать reconciliation (сверку) между DWH и Data Lake еженедельно
  - Хранить сырые данные в неизменяемом формате (Parquet) в Data Lake
- **Метрика**: Расхождение данных ≤ 0,001%, RPO = 0 при миграции

### R6 — Несоответствие требованиям регуляторов

- **Тип меры**: Технический + Организационный
- **Меры**:
  - Внедрить Data Classification — маркировка данных по уровню чувствительности
  - Настроить аудит доступа ко всем Data Products
  - Привлечь комплаенс-офицера для ревью архитектуры
  - Использовать шифрование at rest и in transit (TLS + KMS)
  - Реализовать механизм Data Retention — автоматическое удаление данных по истечении срока хранения
- **Метрика**: Успешное прохождение аудита ЦБ и Минздрава

## Риски с приоритетом «Средний»

### R3 — Деградация производительности Event Bus

- **Тип меры**: Технический
- **Меры**:
  - Заложить нагрузочное тестирование Kafka на старте (определить лимиты)
  - Использовать partitioning по ключам доменов
  - Внедрить Auto Scaling для Kafka кластера
  - Мониторить Consumer Lag через Prometheus + алерты при превышении порога
- **Метрика**: Consumer Lag < 1 сек при пиковой нагрузке

### R5 — Vendor lock-in (Yandex Cloud)

- **Тип меры**: Технический
- **Меры**:
  - Использовать open-source технологии (Kafka, Flink, Kubernetes) без proprietary-расширений
  - Хранить данные в S3-совместимом хранилище (без привязки к API провайдера)
  - Terraform-модули проектировать мульти-провайдерными (абстракция через переменные)
- **Метрика**: Более 80% инфраструктуры может быть развёрнуто у другого провайдера без изменений кода

### R7 — Сопротивление команды

- **Тип меры**: Организационный
- **Меры**:
  - Провести сессии «architecture kick-off» с демонстрацией выгоды для разработчиков
  - Организовать внутренние митапы и tech talks
  - Назначить ambassador'ов (по 1 из каждой команды) для коммуникации изменений
  - Внедрять изменения итеративно, показывая быстрые победы (quick wins)

### R13 — Нестабильность CDC из SQL Server 2008

- **Тип меры**: Технический
- **Меры**:
  - Использовать логирование транзакций (transaction log tailing) вместо триггеров
  - Реализовать fallback — периодическую полную выгрузку (full dump) для сверки
  - Мониторить состояние CDC-коннектора и перезапускать при сбое
  - Иметь план Б — миграция данных через промежуточный SQL Server 2019+

### R15 — Рост затрат на инфраструктуру

- **Тип меры**: Технический + Организационный
- **Меры**:
  - Настроить бюджеты и алерты по затратам в Yandex Cloud (budget alerts)
  - Использовать spot-инстансы для batch-обработки (Flink)
  - Ввести практику FinOps — регулярный пересмотр использования ресурсов
  - Оптимизировать retention данных (горячие → холодные → удаление)

### R2 — Несовместимость протоколов событий

- **Тип меры**: Технический
- **Меры**:
  - Внедрить Schema Registry (Avro / Protobuf) с обязательной проверкой совместимости
  - Утвердить корпоративный стандарт на формат событий (CloudEvents spec)
  - Автоматизировать проверку совместимости схем в CI/CD пайплайне

## Риски с приоритетом «Низкий» — мониторинг

### R4 — Утечка данных через витрину

- **Меры**: RBAC + Data Masking + Audit Logs. Регулярный пентест Data Marketplace.

### R14 — Потеря событий при сбое Kafka

- **Меры**: min.insync.replicas=2, acks=all, retention 7 дней на DLQ. Регулярное резервное копирование Kafka в S3.

### R9 — Конфликт границ доменов

- **Меры**: Event Storming сессии с участием всех подразделений. Назначить Domain Architect'а для разрешения споров.

## План действий по этапам

| Этап | Срок | Фокус | Ключевые риски |
|------|------|-------|----------------|
| 1 | 0–6 мес | Пилот в 1–2 доменах (финансы, пациенты) | R8, R11, R13 |
| 2 | 6–18 мес | Масштабирование на критические домены | R1, R3, R6, R12 |
| 3 | 18–36 мес | Отказ от легаси, переход к событийной платформе | R5, R15, R4 |

Каждый этап завершается ретроспективой с переоценкой рисков и корректировкой плана управления.
